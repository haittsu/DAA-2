# Assignment 2 — индивидуальный отчёт по анализу алгоритмов

## 1. Overview

Проект сравнивает три собственные структуры для целых чисел: [DynamicArray](src/DynamicArray.java) с удвоением внутреннего массива, [LinkedList](src/LinkedList.java) с головой и хвостом и [MinHeap](src/MinHeap.java) на массиве. Цель — доказать корректность характерных операций, сопоставить асимптотику с измерениями и выбрать структуру под конкретную нагрузку. Стандартные коллекции Java используются в [тестах](src/Tests.java) как эталон, а не как основа реализаций.

Исходный набор измерений — [benchmark.csv](results/tables/benchmark.csv). В нём 56 строк для четырёх workload, четырёх значений n и всех применимых структур и операций. Графики находятся в [results/plots](results/plots/); скрипт их построения — [plot_benchmarks.ps1](tools/plot_benchmarks.ps1).

### Запуск

Нужен JDK с командами javac и java в PATH; сторонние библиотеки не требуются. Из корня репозитория:

~~~text
javac src/Main.java src/DynamicArray.java src/LinkedList.java src/MinHeap.java src/Tests.java src/Benchmark.java
java -cp src Tests
java -cp src Benchmark
powershell -NoProfile -ExecutionPolicy Bypass -File tools/plot_benchmarks.ps1
~~~

Последние две команды соответственно перезаписывают CSV новыми *реальными* измерениями и строят графики по текущему CSV. Main — лишь проверка запуска проекта.

## 2. Асимптотическая сложность

Здесь n — размер структуры **перед отдельным вызовом**. Анализ относится к корректным индексам; проверка неверного индекса сама занимает Θ(1). Во всех столбцах случаев указана **точная граница Θ(f)**: она одновременно даёт верхнюю границу O(f) и нижнюю Ω(f) для данного случая. Столбец «Общие O / Ω» даёт границы по *всем* допустимым входам: между ними может не быть единой Θ, когда лучший и худший случаи различаются. «Доп. память» означает память, выделенную во время вызова сверх уже существующей структуры; основной массив или узлы в целом занимают Θ(n). Средний случай ниже всегда привязан к указанной модели, а не приписывается любому распределению входов.

Для get(index) и вставки/удаления по индексу в среднем индексы равномерны среди допустимых позиций. Для contains(x) успешный поиск имеет равномерную позицию первого совпадения либо запрос отсутствует с ненулевой постоянной вероятностью; в обоих случаях математическое ожидание длины просмотра — Θ(n). Для кучи при оценке среднего случая новые ключи независимы и равномерны, а рост массива учитывается амортизированно. При n=0 особые случаи пустой структуры описаны в тестах, но не меняют асимптотику при растущем n.

### DynamicArray

| Операция | Лучший Θ | Средний Θ | Худший Θ | Общие O / Ω | Доп. память |
| --- | --- | --- | --- | --- | --- |
| add(x), в конец | 1 | 1 амортизированно | n | O(n), Ω(1) | Θ(1) без роста; Θ(n) при росте |
| add(index, x) | 1 | n | n | O(n), Ω(1) | Θ(1) без роста; Θ(n) при росте |
| remove(index) | 1 | n | n | O(n), Ω(1) | Θ(1) |
| get(index) | 1 | 1 | 1 | O(1), Ω(1) | Θ(1) |
| contains(x) | 1 | n | n | O(n), Ω(1) | Θ(1) |
| size() | 1 | 1 | 1 | O(1), Ω(1) | Θ(1) |

При add(x) свободная ячейка требует одной записи; если массив полон, копируются n элементов, поэтому **один вызов** стоит Θ(n). Удвоение ёмкости даёт менее 2m дополнительных копирований за m последовательных добавлений после начальной ёмкости, так что средняя по длинной последовательности стоимость одного append — Θ(1) **амортизированно**, а не гарантия Θ(1) для каждого вызова или «случайное среднее». При add(index, x) сдвигаются n-index элементов, затем записывается новый; средний равномерный индекс даёт Θ(n). При remove(index) сдвигаются n-index-1 элементов; удаление последнего постоянно. get обращается к одной ячейке, contains останавливается на первом совпадении либо просматривает весь массив. Временный новый массив при расширении требует Θ(n) памяти на пике.

### LinkedList

| Операция | Лучший Θ | Средний Θ | Худший Θ | Общие O / Ω | Доп. память |
| --- | --- | --- | --- | --- | --- |
| add(x), в хвост | 1 | 1 | 1 | O(1), Ω(1) | Θ(1) |
| add(index, x) | 1 | n | n | O(n), Ω(1) | Θ(1) |
| remove(index) | 1 | n | n | O(n), Ω(1) | Θ(1) |
| get(index) | 1 | n | n | O(n), Ω(1) | Θ(1) |
| contains(x) | 1 | n | n | O(n), Ω(1) | Θ(1) |
| size() | 1 | 1 | 1 | O(1), Ω(1) | Θ(1) |

Хвостовой указатель делает add(x) постоянным. add(0, x) и remove(0) меняют несколько ссылок; вставка в хвост через add(index, x) тоже использует хвост. Для других индексов односвязный список идёт от головы к предшественнику, поэтому вставка/удаление в середине и удаление последнего стоят Θ(n); хвостового указателя недостаточно для удаления последнего без предшественника. get(index) проходит index+1 узлов, а contains сравнивает значения до совпадения или конца. Каждый новый узел требует Θ(1) дополнительной памяти.

### MinHeap

| Операция | Лучший Θ | Средний Θ | Худший Θ | Общие O / Ω | Доп. память |
| --- | --- | --- | --- | --- | --- |
| insert(x) | 1 | 1 ожидаемо и амортизированно | n при росте; log n без роста | O(n), Ω(1) | Θ(1) без роста; Θ(n) при росте |
| peekMin() | 1 | 1 | 1 | O(1), Ω(1) | Θ(1) |
| extractMin() | 1 | log n ожидаемо | log n | O(log n), Ω(1) | Θ(1) |
| size() | 1 | 1 | 1 | O(1), Ω(1) | Θ(1) |

siftUp и siftDown проходят не более высоты двоичной кучи, Θ(log n). Для независимых случайных ключей вставленный ключ обычно поднимается лишь на небольшое число уровней; в принятой модели ожидаемая стоимость siftUp — Θ(1). Это **не** отменяет худший путь Θ(log n). Реализация insert также удваивает полный внутренний массив: такой отдельный вызов стоит Θ(n), хотя суммарная стоимость расширений за последовательность вставок линейна. peekMin читает корень. extractMin может остановиться сразу, но обычно перемещает последний элемент по высоте дерева; он не уменьшает ёмкость массива и не выделяет новый массив. Для пустой кучи peekMin/extractMin выбрасывают NoSuchElementException.

## 3. Два доказательства корректности

### 3.1 DynamicArray.add(index, x): цикл сдвига вправо

Пусть до вызова размер s, допустимый индекс k находится в [0, s], а прежние значения обозначены A[0], …, A[s-1]. ensureCapacity сохраняет этот префикс и предоставляет ячейку s. Цикл выполняет присваивания elements[i] = elements[i-1] при i = s, s-1, …, k+1.

1. **Инвариант перед итерацией с i.** Ячейки [i+1, s] уже содержат A[i], …, A[s-1] соответственно; ячейки [0, i-1] по-прежнему содержат исходные A[0], …, A[i-1]. Поэтому источник elements[i-1] ещё не перезаписан.
2. **Инициализация.** При i=s перенесённый суффикс пуст, а весь исходный префикс [0, s-1] сохранён после ensureCapacity. Инвариант выполнен.
3. **Сохранение.** Присваивание elements[i] = elements[i-1] кладёт A[i-1] в его новую позицию i. Старые элементы [0, i-2] не меняются. После уменьшения i на единицу инвариант верен для следующей итерации.
4. **Завершение.** Величина i-k уменьшается на каждом шаге и не бывает отрицательной, значит цикл завершится при i=k. Тогда [k+1, s] равен прежнему [k, s-1], а [0, k-1] не менялся.
5. **Вывод.** Запись x в elements[k] и увеличение size до s+1 дают ровно исходный префикс, затем x, затем исходный суффикс. Порядок и число прежних элементов сохранены. При k=s цикл пуст и это обычный append; при k=0 сдвигается весь массив.

### 3.2 MinHeap.extractMin(): цикл siftDown

До вызова все родители не больше детей, поэтому корень есть минимум. При непустой куче extractMin сохраняет значение корня, перемещает последний элемент в корень и уменьшает size. Если остаётся один или более элементов, siftDown идёт от корня. Все поддеревья ниже корня сохраняют свойство кучи, а множество оставшихся значений не изменено перестановкой.

1. **Инвариант перед итерацией в позиции p.** Все рёбра дерева, кроме возможно рёбер от p к его детям, удовлетворяют порядку кучи; значения оставшихся элементов те же, что до siftDown. Для p не в корне его родитель не больше значений обоих детей p, оставшихся от упорядоченного поддерева.
2. **Инициализация.** После замены корня последним элементом нарушиться могут только рёбра от корня. Корень не имеет родителя, остальные поддеревья были корректными. Инвариант выполнен.
3. **Сохранение.** Цикл выбирает меньшего ребёнка c. Если elements[p] ≤ elements[c], оба ребёнка не меньше p и обмен не нужен. Иначе обмен ставит c в p: он меньше прежнего p и не больше второго ребёнка. Ребро к родителю p тоже корректно по инварианту и прежнему порядку поддерева. Возможное нарушение теперь только у перемещённого элемента в c; множество значений сохранилось, значит инвариант выполнен для новой p=c. При равенстве обмен не производится.
4. **Завершение.** При каждом обмене p уходит строго вниз, а высота конечна; цикл достигает листа либо прекращается, когда p не больше меньшего ребёнка.
5. **Вывод.** По инварианту и условию остановки теперь упорядочены все рёбра, следовательно оставшийся массив — min-heap. Возвращён старый корень, то есть минимум исходной кучи. При одном исходном элементе siftDown не запускается и возвращается единственное значение.

## 4. Методика эксперимента

[Benchmark.java](src/Benchmark.java) запускает четыре фиксированных workload при **n = 100, 1 000, 10 000, 100 000**, где n — исходное число элементов. Для random access m=10 000 вызовов get со случайными индексами; для search m=1 000 вызовов contains; для insertion/removal m=1 000 вызовов каждой операции в начале и середине; для priority processing отдельно n вставок в пустую кучу и n извлечений. Каждый вариант измерен **пять раз** с Random(42). Значения — целые из [-1 000 000, 1 000 000]; в search половина запросов берётся из исходного набора, половина генерируется независимо (случайные совпадения возможны).

Данные, индексы и ожидаемые ответы создаются до замера. Время получает System.nanoTime(): для get, contains и каждой фазы кучи замеряется цикл целиком, для вставок/удалений суммируются длительности отдельных вызовов. Построение структуры, проверка результата, сброс/чтение счётчиков и печать выполняются вне измеряемых интервалов. Для кучи ожидаемая последовательность сортируется заранее; после извлечений проверяется точное равенство ей. Среднее в CSV — сумма длительностей или счётчиков **одного полного повтора**, усреднённая по пяти повторам; это не время одного вызова. avg_time_ns дан в наносекундах, в таблицах ниже он переведён в миллисекунды и округлён до 0,001 мс. Счётчики в таблицах — точные средние из CSV; пустые поля CSV означают неприменимость метрики.

В опытах вставки сначала создаётся структура из n элементов. Для вставки в середину индекс на шаге i равен (n+i)/2, поэтому он остаётся около середины растущей структуры. **Удаления измеряются из исходного состояния:** после каждого замеренного remove(index) тот же элемент возвращается вызовом add(index, removed) *вне таймера*, затем перед следующим remove счётчики обнуляются. В CSV включены только время и счётчики удалений. Для середины индекс удаления всегда n/2. Это позволяет честно выполнить 1 000 удалений даже при n=100, но время восстановления, которое было бы частью иной прикладной задачи, в сравнении отсутствует.

DynamicArray считает чтения и записи ячеек массива, а «перемещения» — копирование старых элементов при сдвиге/росте. LinkedList считает посещения существующих узлов (вставка в голову даёт ноль посещений, хотя работа и выделение узла происходят). Сравнения значений при contains и siftUp/siftDown считаются отдельно. Запуск сохранённого CSV выполнялся на Windows с OpenJDK 25.0.1. Специальной прогревочной фазы, измерения дисперсии и контроля нагрузки системы нет, поэтому малые различия по времени не следует считать устойчивыми.

## 6. Обсуждение результатов

**Random access.** Для 10 000 get массив делает ровно 10 000 обращений при любом n; список — около 10 000·n/2 посещений (от 506 978,6 до 500 098 218,4). Его время растёт от 0,709 до 728,324 мс, как предсказывает Θ(n) на один случайный get. Время массива не растёт монотонно: 0,160 мс при n=100 и 0,011 мс при n=100000. Это не нарушение Θ(1): число обращений постоянно, а короткий замер зависит от прогрева JIT, кэша, ветвлений и накладных расходов таймера. Считать этот спад ускорением алгоритма с ростом n нельзя.

**Search.** Обе реализации делают одинаковое число сравнений на одинаковых запросах: примерно от 75,6 тыс. до 73,1 млн, что согласуется с Θ(n) на поиск. Около половины запросов гарантированно присутствует; примерно равномерное место совпадения даёт в среднем n/2 проверок, а отсутствующий запрос — n, вместе около 0,75n. Случайные совпадения и дубликаты меняют точную долю. При n=100 LinkedList оказался быстрее (0,271 против 0,397 мс), но при n=100000 DynamicArray быстрее (27,166 против 154,802 мс). При равном числе сравнений массив выигрывает за счёт плотного размещения и последовательного доступа; список разыменовывает ссылки, а запуск на малом n подвержен шуму.

**Insertion/removal.** В начале список меняет ссылки за Θ(1): при n=100000 вставка заняла 0,084 мс, удаление 0,051 мс. Массив за те же 1 000 вызовов переместил соответственно 100 599 500 и 99 999 000 элементов, затратив 11,364 и 9,097 мс. В середине обе структуры имеют Θ(n) на вызов, но при n=100000 массив быстрее: 5,321 против 80,120 мс при вставке и 3,819 против 78,671 мс при удалении. Последовательные сдвиги массива оказываются дешевле обхода примерно 50 млн узлов списка. При n=100 времена вставки в середину совпали до 0,001 мс, а удаление списка было немного быстрее; эти малые отличия не опровергают асимптотику. Значения для вставки при n=100 также отражают несколько расширений начальной ёмкости; 1,361 мс больше, чем 0,256 мс при n=1000, хотя перемещений меньше. Здесь влияют рост, JIT и короткие интервалы. При удалении восстановление вне таймера сохраняет фиксированный n и делает результаты сопоставимыми, но стоимость полного сценария «удалить и восстановить» таблицы не показывают.

**Priority processing.** При n от 100 до 100000 вставки дали 207,8 → 227 781,8 сравнений и 0,044 → 2,029 мс: около постоянного числа сравнений на вставку для случайных ключей, что согласуется с ожидаемым Θ(1) siftUp и амортизированным ростом массива. Извлечения дали 848,8 → 2 831 578 сравнений и 0,065 → 11,327 мс, согласуясь с Θ(n log n) за n операций. Все извлечённые числа сверены с отсортированным исходным массивом. Время не обязано масштабироваться точно как счётчик: расширение массива, копирование, выделение памяти, кэш, JIT, GC и работа таймера имеют разные постоянные затраты. Особенно для вставки в кучу худший отдельный вызов Θ(n) из-за расширения не виден как типичный при усреднении.

Одинаковая Big-O не гарантирует одинаковое время: срединные операции обеих структур имеют O(n), но доступ к соседним ячейкам массива и переход по разрозненным узлам дают разные задержки. И наоборот, конечные n, пять повторов и отсутствие отдельного прогрева не доказывают асимптотический закон только по времени. Счётчики помогают проверить механизм, но измерения относятся лишь к этой реализации и среде запуска.

## 7. Рекомендации по выбору структуры

| Задача | Выбор | Основание |
| --- | --- | --- |
| Частый доступ по индексу | DynamicArray | Θ(1) get; в опыте постоянные 10 000 обращений против сотен миллионов посещений списка при большом n. |
| Поиск значения без индекса | DynamicArray для средних и больших n | У обеих структур Θ(n) и одинаковые сравнения, но массив быстрее при n≥1000 в этом CSV благодаря последовательному доступу. |
| Частые вставки и удаления в голове | LinkedList | Θ(1) вместо Θ(n) сдвигов; преимущество измерено на всех n. |
| Вставка и удаление по индексу в середине | DynamicArray в этой реализации | Обе Θ(n), но при n≥1000 массив измеренно быстрее из-за последовательного сдвига. Если у вызывающего кода уже есть ссылка на предшественника, связный список мог бы менять ссылки за O(1), однако текущий индексный API такой ссылки не принимает. |
| Добавление в конец и затем доступ по индексу | DynamicArray | Append амортизированно Θ(1), get Θ(1); редкие расширения имеют Θ(n). |
| Приоритетная обработка минимума | MinHeap | peekMin Θ(1), extractMin O(log n) на вызов; куча поддерживает порядок приоритетов и выдала отсортированную последовательность. |

## 8. Заключение

Теория и счётчики совпали по основным механизмам: индексный доступ массива постоянен, обход списка и линейный поиск растут с n, фронтальные сдвиги массива дороги, а извлечение из кучи следует высоте дерева. Время показывает те же крупные различия, но на малых размерах и при одинаковой Θ зависит от размещения данных и деталей выполнения Java. Выбор структуры определяется операциями: массив — для индексов и последовательного доступа, список — для изменений в голове, куча — для повторного получения минимума.
